# Driving tasks from a driver session

The driver session (row `driver`, second line `@local`, ⌃⌥⌘D) starts and watches other sessions. Its cwd is the first existing folder in `$WT_REPOS_DIR`, which is not a repo, so every `wt new` needs `-r <repo>`. `wt` hides local/remote: `wt <sub> …` for this Mac, `wt -H <vm> <sub> …` for a VM.

1. **Write the brief.** Turn the request into a self-contained brief: goal, relevant files/areas, done criteria, constraints, base branch if not main. The new session has no memory of this conversation.
2. **Start the task.** Pick a short kebab slug (no dots). `wt new <slug> -r <repo> -a <agent> -p "<brief>"`, or `wt -H <vm> new -r <repo> -a <agent> -p "<brief>"` when the user names a VM. One task per independent unit of work; do not split work that touches the same files.
   When the user gives machine requirements instead of a VM name, run `wt hosts --json` on the Mac immediately before choosing. Consider only `status == "available"` entries with known `cpu_logical` and `memory_mib` meeting the requested minimums. Treat an unqualified "GB" as decimal (1 GB = 10^9 bytes, about 953.7 MiB); use 1024 MiB for an explicit GiB. Compare these converted thresholds with the reported usable RAM and GPU memory, without a percentage tolerance: a stated usable-memory requirement must really fit. A GPU request also requires `gpu_status == "ok"` and at least the requested number of GPUs in `gpus`, each meeting any requested model and memory minimum; a null GPU `memory_mib` cannot meet a memory minimum. The inventory is hardware capacity, not currently free capacity. For a CPU-only task, prefer a host with `gpu_status == "none"`, then the least excess CPU and RAM; for a GPU task, prefer the least excess matching GPU count and memory, then CPU and RAM; break ties by host name. `wt -H <host> new` checks the repo itself; if its preflight says the repo is missing, try the next matching host. If none qualifies, report that and do not create a task. After any other `new` error, follow its inspection or recovery command before selecting another host: SSH may have dropped after the worktree was created.
3. **Report each task**: name, row title (`<repo>:<slug>`, second line `@local` or `@<vm>`), branch, path, and on a VM the tmux session.
4. **Progress on request**: `wt list [--all]`, `wt show <name>`, `wt -H <vm> list`, `wt -H <vm> show -r <repo> <name>`. Open code only when asked: `wt open <name>` / `wt -H <vm> open -r <repo> <name>`. For a suspended VM task row after a network switch, `wt -H <vm> attach -r <repo> <name>` clears that row's stale SSH relay and reconnects it. The same command re-opens a row after a lost pty; add `--reattach` if a connected row shows a bare shell after a dropped connection, or `--restart-agent` only if attach refuses because no agent is running, and only when the user asks.
5. **Do not do the work here.** Never do a task's own coding in the driver session, and never remove worktrees unless asked — `wt rm <name>` / `wt -H <vm> rm -r <repo> <name>` under the `worktree-teardown` rules.
6. **First task per repo on a VM**: tell the user to click the row once and accept the agent's trust prompt (one per repo; worktrees inherit it). After a hook change, Codex asks once via `/hooks`.
